# 多職種間の「前提」を埋めるアプリ コンセプトシート

Nov 5, 2026 · @tomo

> ハッカソン発表用（発表日：2026年11月10日）。決まったことを順に追記していく。

**初めて読む人は、この3つ：** 方向（このタブ）・今できること・仕組み

## 1. 背景：訪問薬局へのインタビュー

訪問薬局の薬剤師さんに困りごとを聞いたところ、次の2つが挙がった。

- 「医者からチューブを2本持っていくように言われたが、**なぜその本数なのか分からなかった**。」
- 「医者にチューブが足りないと言われて多めに持って行ったら、**多すぎて返品された**。」

どちらも、医師の頭の中にある\*\*根拠（患者の状態、使用量、交換頻度など）\*\*が薬剤師に伝わっていないことが原因と考えられる。

## 2. 課題

- 指示を出す側は、自分が前提にしている情報を「相手も知っている」と思い込んで話す。
- 受け取る側は、その前提が分からないまま動くため、量の過不足や手戻りが起きる。
- 職種が違うと知識や見ている情報が違うため、このずれが起きやすい。

**私たちの考え：**職種が違っても、互いが**根拠を持って伝える**ことで認識の差が小さくなり、ミスが減る。

## 3. コンセプト

**一言で言うと：**

> 医療の多職種間の会話で、**一方は分かっているがもう一方は分かっていない前提**をAIが予測し、伝える前に埋めるWebアプリ。

やりたいこと：

- 一方が前提として話していることを、もう一方も把握できるようにする。
- 相手が理解していないものを、伝える段階で補う。
- 結果として、多職種間の認識の差を小さくする。

## 4. 誰が使うか

| 組み合わせ | 送り手 | 受け手 | 起きやすいずれ |
| --- | --- | --- | --- |
| 医師 ⇄ 薬剤師 | 医師 | 薬剤師 | 指示（本数・量など）の**理由**が分からない |
| 医師 ⇄ 患者 | 医師 | 患者 | 医師の説明（専門用語や前提知識）が分からない |

## 5. AIの役割

AIは\*\*「相手が何を分からないか」を予測する\*\*ために使う。

- **指示内容の理由**：例「チューブ2本」→ 薬剤師は「なぜ2本か」が分からないはず、と予測する。
- **医師の言うことで患者が分からないこと**：専門用語や、患者が知らない前提を予測する。

## 6. 形と制約

- 形式：Webアプリ
- 用途：ハッカソンでの発表
- 締め切り：2026年11月10日

## 7. 決定事項

**AIが予測した「分からない点」の扱い：**

- **送り手には補足を促す。** 例：医師が「チューブ2本」と入力すると、AIが「薬剤師は本数の理由が分からない可能性があります。根拠を補足しますか？」と提示する。
- **患者には「質問リスト」として見せる。** AIが予測した分からない点を一覧にして、患者が医師に質問しやすくする。

**最初に作る機能（MVP）：**

1. 送り手（医師）が指示や説明を入力する。
2. AIが、受け手に分からなさそうな点を予測してリストアップする。
3. そのリストを送り手と受け手の両方に表示する。

**使う場面：** 対面とオンラインの両方を想定する。オンラインでの使い方は後で決める。

**対面での使い方（2026年11月6日決定）：**

送り手A と受け手B の会話に、システムが入る。端末は1台で、B が持つ。

1. A が話す。
2. システムが文字起こしする。
3. AI が、文字起こしの中から B にとって難しそうな語を見つける。
4. B が A の話を聞き終えたあと、画面に「〇〇は分かりますか？」と出す。
5. B が「はい／いいえ」で答える。
   - はい → 何もしない。
   - いいえ → その語を質問リストに入れる。
6. 質問リストは画面上部の一部に常に出しておき、スクロールで全部を見られる。
7. 会話のキリが良くなるまで、1〜6 を続ける。
8. キリが良くなったら、質問リストを B に見せ、A に直接質問するよう促す。
9. B が A に質問できたら、質問リストを空にする。
10. 会話が続く限り、1〜9 を繰り返す。

**AIは受け手の疑問に答えない。** AIで答えを作ることもできるが、医療で使うシステムであり、誤った答えは命に関わるおそれがある。そのため、AIは「分からない語を見つける」までにとどめ、答えは必ず A に直接聞いてもらう。

## 8. 未決事項

- アプリ名（後で決める）
- オンラインでの具体的な使い方
- 対面の流れの細部（下の「対面の流れで決めること」）
- MVP（入力欄に打つ流れ）と、対面の流れ（話して文字起こしする流れ）の関係：置き換えるか、両方作るか

**対面の流れで決めること：**

- 「B が聞き終えた」を、システムがどう判断するか（A の話が途切れたら／B がボタンを押したら など）
- 「キリが良くなった」を、誰がどう決めるか（B がボタンを押す／A が言う など）
- 「B が質問できた」を、システムがどう知るか（B がボタンを押す など）
- 一度「はい」「いいえ」と答えた語が、また出てきたら聞き直すか
- 見つけるのは難しい語だけか、ほかの観点（なぜ必要か・いつどのくらい など）も含めるか
- A と B は誰か（医師と患者だけか、医師と薬剤師も含めるか）
- 発表で見せるデモの流れ

## 9. 決定の記録

決めたこと・理由・却下した案を残す。理由がないと、後から読むAIが「改善」のつもりで覚すため。

| 決めたこと | 理由 | 却下した案 |
| --- | --- | --- |
| 送り手に補足を促す（AIは根拠を書かない） | 根拠は送り手の頭の中にしかない | AIが理由を推測して受け手に説明する |
| 患者には質問リストで見せる | 患者が医師に質問しやすくするため | 未記入 |
| 正本は手元のMarkdownにする | オンラインのドキュメントはコンセプトシートで、Markdownの元。他のAIはファイルを読む | オンラインのドキュメントを正本にする |
| 観点リストはコードで固定する | ルール4。結果を再現できるようにする | AIに観点を自由に選ばせる |
| Next.js + TypeScript、Gemini API、Cloud Run で作る | 画面とAPIを1つで作れ、1コンテナでデプロイできる。Googleハッカソンのため | Python FastAPI + 素のHTML、Firebase Hosting + Functions |
| 対面では端末1台を受け手Bが持ち、Aの話を文字起こしする | 会話の流れを止めずに、Bが自分の分からない点を確かめられる | 未記入 |
| 難しい語はBに「分かりますか？」と聞き、「いいえ」の語だけを質問リストに入れる | AIの予測をそのまま信じず、本当に分からない語だけを残すため | 未記入 |
| AIはBの疑問に答えを作らず、Aに直接質問するよう促すだけにする | 医療で使うため、AIの誤った答えが命に関わるおそれがある | AIが語の意味や答えを説明する |
| コードと設定は `app/` にまとめ、直下は README と文書だけにする | 非エンジニアも見るため、直下に設定ファイルを並べない | 直下にコードを置く／文書も `docs/` に移す |
