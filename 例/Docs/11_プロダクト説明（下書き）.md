# 【必須項目】

## 1. プロジェクト概要

「[アプリ名]」は、医療・介護の会話の中で、聞く人が「前提が要りそうな言葉」に会話の最中に気づき、その場で話す人に聞けるようにする Web アプリケーションです。

聞く人が手元の端末で会話を聞き取ると、Gemini が、聞く人の職種から見て分かりにくそうな言葉（専門用語・略語・理由や量の前提）を見つけ、画面の下にそっと「〇〇は分かりますか？」と出します。「いいえ」と答えた言葉は画面上部のリストに残り、聞く人は会話の区切りで話す人に直接質問できます。

- **対象**：医師・患者・薬剤師・看護師・介護者。話す人と聞く人は、この5職種のどの組み合わせでもよい
- **目的**：職種による前提のずれを、会話の中で小さくすること
- **安全性**：AI は言葉の意味や答えを書かない。答えは必ず話した本人に聞く

## 2. 解決する課題

### 2.1. 対象ユーザー

- 医師・薬剤師・看護師から、指示や説明を受ける人（薬剤師・看護師・患者・介護者）
- 患者や家族に説明をする医療・介護の専門職
- 職種の違う相手と、在宅医療・訪問の現場で話す人

### 2.2. 課題と根拠

訪問薬局の薬剤師へのインタビュー（2026年11月5日）で、次の2つの困りごとを聞きました。

- 「医者からチューブを2本持っていくように言われたが、なぜその本数なのか分からなかった。」
- 「チューブが足りないと言われて多めに持って行ったら、多すぎて返品された。」

どちらも、医師の頭の中にある根拠（患者の状態・使用量・交換頻度）が、薬剤師に伝わっていないことが原因です。
話す人は「相手も知っているはず」と思って話し、聞く人はその前提を知らないまま動くため、量の過不足や手戻りが起きます。職種が違うほど、知っていることも見ている情報も違うので、このずれは医師と薬剤師だけでなく、患者・看護師・介護者のどの組み合わせでも起きます。
さらに聞く人は、「自分が何を分かっていないか」に自分では気づきにくく、気づいても会話の流れを止めて聞きにくい、という難しさがあります。

### 2.3. 既存手法との違い

| 観点 | 従来（その場で聞く・あとで問い合わせる） | [アプリ名] |
| --- | --- | --- |
| 分からない点への気づき | 聞く人が自分で気づく必要がある | 職種に合わせて、前提が要りそうな言葉を AI が先に見つける |
| 会話への影響 | 話をさえぎって聞くか、聞きそびれる | 画面の下にそっと出すだけ。聞くタイミングは聞く人が決める |

| 使える人 | — | ふりがな・大きな文字・押しやすいボタンで、高齢の患者や介護者も使える |

### 3.3. Google 技術を選定した理由

本プロジェクトの中心は、「職種の違う相手にとって、どの言葉が分かりにくいか」を会話のたびに判断することです。これは決まった辞書では作れないため、日本語の会話を読み、話す人と聞く人の職種を踏まえて言葉を選べる Gemini を採用しました。Gemini は返す形（JSON）を決められるので、返ってきた言葉が発言の中にあるか・説明文が混じっていないかを、コードで検査できます。

医療で使うため、AI に言葉の意味や答えを書かせない設計にしました。Gemini には「言葉と読みだけ」を返させ、それ以外はコードで捨てます。

実行基盤には Cloud Run を選びました。画面と API を1つのアプリ（Next.js）として作り、1つのコンテナで公開できるため、約6日間の開発期間で「動くもの」を最後まで届けられると考えました。会話はどこにも保存しない設計なので、データベースは使っていません。Gemini は Vertex AI 経由で呼び、API キーではなく Cloud Run のサービスアカウントで認証しています。

比べた案：Firebase Hosting＋Functions（画面と API が分かれ、短い期間では手間が増える）、Flutter（ネイティブアプリより、URL を開くだけで使える Web のほうが現場で試しやすい）、Google AI Studio の API キー（配られたクレジットが使えず、キーの管理も要る）。

## 4. アーキテクチャ図

下書き：`例/Docs/構成図.svg`。**提出前に Google Cloud の公式アイコンで描き直す。**

流れ：

1. 聞く人の端末（ブラウザ）が、話す人の声を文字にする
2. 確定した発言を、HTTPS で Cloud Run の `/api/detect` に送る
3. Cloud Run が呼び出し回数と長さの上限を確かめ、指示文を作って Vertex AI の Gemini に送る
4. Gemini が「前提が要りそうな言葉と読み」を JSON で返す
5. Cloud Run が検査し（発言にない言葉・説明文を捨てる）、端末に返す
6. 端末が画面の下に「分かりますか？」を出し、答えと質問リストは端末の中だけで持つ（保存しない）

| 必要なもの | マイク（ブラウザでマイクの使用を許可する） |

### 6.2. 動作確認手順

1. 上記 URL を開きます。
2. ホーム画面で、「話す人」に「医師」、「聞く人」に「患者」を選び、「はじめる」を押します。
3. 「聞き取りを始める」を押し、ブラウザのマイクの使用を許可します。
4. 下のサンプルの文を、話す人の役で読み上げます。
5. 画面の下の暗い帯に「「NSAIDs」は分かりますか？」と出ることを確かめます（ふりがな付き）。
6. 「いいえ」を押すと、言葉が画面上部のリストに入ります。5秒間は「取り消す」で戻せます。
7. リストの行を押すと印（✓）がつき、リストの上のほうへ移ります。もう一度押すと外れます。
8. 同じ言葉をもう一度読み上げると、聞き直さずに、リストのその行が光ります。

### 6.3. サンプルデータ

ログインもデータの登録もありません。会話は保存しないので、次の架空の文を読み上げて試します。

- 「NSAIDsを毎食後に服用してください。痛いときは頓服で使ってください。」（医師 → 患者）
- 「褥瘡の処置には、この軟膏を1日2回塗ってください。」（看護師 → 介護者）
- 「eGFRが低いので、この薬は減量を提案します。」（薬剤師 → 医師。医師には分かる言葉なので、出ないことを確かめる）

### 7.1. 主な機能

| # | 機能 | 内容 |
| --- | --- | --- |
| 1 | 職種を選ぶ | 話す人と聞く人を、医師・患者・薬剤師・看護師・介護者から選ぶ。同じ言葉でも、聞く人の職種で「分かりにくいか」が変わる |

| 7 | 誰が持っても使える | ふりがな（画面の文言と見つけた言葉）、色だけに頼らない表示、押しやすいボタン、端末の文字サイズ設定に合わせた文字 |

## 8. AI をどの場面でどう使用したか、なぜその場面で使用したか

[下書き。チームで直す]

本プロジェクトでは、プロダクトの中と開発の両方で AI を使いました。

- **プロダクトの中**：前提が要りそうな言葉を見つける場面に Gemini を使いました。職種によって分かりにくい言葉は変わり、決まった辞書では拾えないためです。一方で、言葉の意味や疑問への答えを AI に書かせることはしませんでした。医療では、AI の誤った答えが命に関わるおそれがあるためです。
- **開発**：[開発で使った AI ツール] を、要件の整理、コードとテストの作成、文書づくりに使いました。AI の案は複数出させて比べ、選んだ理由と捨てた案を「決定の記録」に残しました。たとえば、最初に AI と作った「話す人が入力し、AI が補足を促す」案は、対面の会話にそのまま入れないため、採用しませんでした。
- **確かめ方**：AI の出力は文章どうしを比べず、「発言にない言葉を返さない」「受け手が分かるはずの言葉は出さない」といった条件で検査する自動テストを作りました。
